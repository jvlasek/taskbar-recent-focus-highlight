## Draft PR comment

Thanks. The immediate `SetEvent` was a real unload hole. This is v0.9.34.

**1. Unload could return while cleanup was still queued — agreed. The High-operation fallback is not what we shipped.**

High work is allowed to run ahead of Normal work already in the queue. Waiting for the High cleanup to finish proves that callback returned. It does not prove those older callbacks have finished, and they still execute in this mod. A failed `Completed` subscription is also not the same thing as “nothing was queued.”

Unload now returns only when one of these is true:

- The Low sentinel’s operation completed and `GetResults()` is true, so that callback ran. It is posted after the High cleanup, so it runs after that cleanup and after Normal work already queued.
- The dispatcher object is disconnected or closed (`RPC_E_DISCONNECTED`, server died, not connected, or `RO_E_CLOSED`). Further posts cannot be observed. That is a weaker exit than a sentinel that ran, and it is logged. A generic exception is not this case.

`Completed` still signals the waiter when it can be set. If it cannot, we poll `Status()`. A status read that throws is not treated as completion. `HasThreadAccess` and `ProcessEvents` use the same split, so a throw from those calls does not escape `Wh_ModUninit`.

`TryRunAsync` completing with `false` is the documented shutdown rejection. It means that post was not accepted. It does not show that work already queued will not run, so it is not a drain and it does not end the wait. There is no two-second or thirty-second path that unloads anyway.

**2. Line count — leaving it for the human reviewer.**

Not collapsing the per-dispatcher helpers. Primary and secondary taskbars share one Explorer UI thread here, but one dispatcher would not make the unload wait correct. App highlights and preview highlights both stay.
