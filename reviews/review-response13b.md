### Required: dispatcher shutdown

`RememberUiDispatcher` captures a real `SYNCHRONIZE` thread handle with `DuplicateHandle` while on the owning UI thread. The dispatcher record retains that handle until cleanup. It does not reopen a stored thread ID at unload: IDs can be reused, and an `OpenThread` failure does not prove the original thread exited.

The unload sequence stops and joins the focus worker, runs High-priority UI cleanup, then observes completion of the Low-priority sentinel. `ObserveDispatcherOp` waits for either the completion event or the retained thread handle. Polling and retry paths also check that handle; only `WAIT_OBJECT_0` establishes thread termination. If event creation or completion subscription fails, it observes the same operation by polling. On the owning thread, it pumps instead of blocking that dispatcher. An operation whose status or result cannot be read is retained rather than discarded and replaced.

The HRESULT-based dispatcher-termination classification is gone. A disconnected-object exception, rejected post, cancellation or error does not establish that earlier callbacks can no longer execute.

**Remaining limitation:** if a dispatcher permanently rejects work while its original thread remains alive, unload still waits and logs the rejection once. Thread termination is now an independent exit condition, including while an operation is pending, but it does not guarantee every shutdown dispatcher will terminate its thread or accept a later sentinel. I have retained this conservative behavior rather than returning after a timeout. Thus the missing thread-exit path is addressed; unconditional unload progress is not claimed.

Dispatcher records are not pruned during capture. Normal dispatch skips terminated threads, unload recognizes them immediately, and resetting the list releases the handles and dispatcher references. This leaves the optional resource-pruning improvement open.
