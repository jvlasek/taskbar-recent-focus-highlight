The local v0.9.35 changes add owning-thread termination as an independent exit condition, with some differences from the suggested implementation. I am testing this version on Windhawk 1.7.3 before pushing it.

### Required: dispatcher shutdown and the retry loop

`RememberUiDispatcher` now captures a real `SYNCHRONIZE` thread handle with `DuplicateHandle` while running on the owning UI thread. The handle stays with the dispatcher record until cleanup. I do not reopen a saved thread ID at unload: IDs can be reused, and an `OpenThread` failure does not establish that the original thread exited.

The unload path now:

- Stops and joins the focus worker first.
- Runs High cleanup, then waits for successful completion of the Low sentinel.
- When using a completion event, waits for either that event or the original thread handle to become signaled. A pending operation therefore cannot strand the wait after its owning thread has exited.
- Checks the retained thread handle during polling and retry paths too. Only `WAIT_OBJECT_0` establishes thread termination; a failed wait does not.
- Retains an operation whose status/result cannot be read, rather than dropping it and posting a replacement.
- Uses polling if event creation or completion subscription fails, and pumps on the owning thread rather than blocking its own dispatcher.

The HRESULT-based “dispatcher gone” classification is removed. Neither a disconnected-object error nor a rejected post is treated as proof that earlier callbacks are gone.

**Remaining limitation:** if the dispatcher permanently rejects work while its original thread remains alive, unload still waits, with a diagnostic logged once. Thread termination is an additional reliable exit condition, not a guarantee that every closed dispatcher will terminate its thread or later accept a sentinel. I am explicitly retaining the conservative behavior for that case rather than introducing a timeout or claiming the hang is impossible.

The dispatcher list is not pruned during capture in this patch. Normal dispatch skips records whose retained thread handle is signaled; unload recognizes those records immediately. Their handles and dispatcher references are released when the list is reset. Pruning remains a possible resource cleanup improvement, not the mechanism used to make unload progress.

### Optional items

- **Magic HRESULT literals:** removed with the entire HRESULT classification helper, rather than replaced with named constants.
- **`ExceptionMeansDispatcherGone` and bare `throw;`:** removed. The drain no longer interprets exceptions as thread termination.
- **Separate High/Low completion events:** left unchanged. One event per dispatcher is reused sequentially. The ordinary subscribed path observes High completion before using the event for Low. Uncertain operation observation retains that operation. I have not added separate events solely to protect against a hypothetical future change.
